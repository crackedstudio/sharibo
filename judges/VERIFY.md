# Verify Sharibo in under a minute

No toolchain installation required for steps 1–2. Everything here checks the deployed testnet contract directly.

## 1. The accepted proof is a real, successful transaction

```bash
curl -s https://horizon-testnet.stellar.org/transactions/2258397474e3ad420d6dd8310cb0976d270c29ec4a4ec2b60a9ae58408088087 \
  | grep -E '"successful"|"ledger"'
```

**Expected output:**

```
  "successful": true,
  "ledger": 3379702,
```

This transaction called `claim()` on the deployed Sharibo contract with a real Groth16 proof, generated by the actual `circuits/membership.circom` pipeline in this repo — not a mock, not a pre-canned fixture.

## 2. Read the live contract state (requires the [`stellar` CLI](https://developers.stellar.org/docs/tools/cli))

```bash
stellar contract invoke \
  --id CB64IZIBBSPUY63UMIVACKWDKRFNH6WJ2EPAOLM7QR4ZI6IJOT4N2LCF \
  --network testnet -- get_circle --circle_id 0
```

**Expected output (abbreviated):**

```
{"admin":"G...","contribution":"50000000","pot":"50000000","round":1,"size":1,"token":"CDLZ...","vk":{...}}
```

`round: 1` (not `0`) is the tell — it only increments after a `claim()` call has succeeded for real, which requires the on-chain Groth16 pairing check to have passed.

## 3. Try to fool it (optional, requires the repo cloned + built — see main README "Run it")

```bash
npm run e2e
```

This script funds a fresh 5-member circle, submits a real proof, claims to a brand-new address, then deliberately replays the _same_ proof's nullifier against a newly funded round and asserts that the contract rejects it with `Error(Contract, #4)` (`AlreadyClaimed`). If any of this were faked, this script would fail loudly — it asserts on live testnet responses, not local state.

## 4. Or just look

- Contract: https://stellar.expert/explorer/testnet/contract/CB64IZIBBSPUY63UMIVACKWDKRFNH6WJ2EPAOLM7QR4ZI6IJOT4N2LCF — five deposits in, one payout out, no visible link between them.
- Live app (click through the whole flow yourself, generating your own proof in your own browser): see the README's "live app" link.

## What this does _not_ prove

- **The proof does not bind the payout address.** `recipient` is a plain `claim` argument, not a circuit input: anyone who sees a pending claim's proof and public inputs — a mempool watcher, a careless or malicious relayer — can copy them, resubmit with a different `recipient`, and redirect the pot (a front-running race the attacker can win). This is a known, documented limitation — see [docs/threat-model.md](docs/threat-model.md), tracked in [issue #246](https://github.com/crackedstudio/sharibo/issues/246) — and it is **not** exercised by any check in this file. Sharibo is testnet-only with no real funds; do not evaluate it for real-funds use until the recipient is bound inside the circuit.
- Verifying these transactions confirms the contract genuinely checked a real Groth16/BLS12-381 pairing on-chain — it doesn't independently re-audit the circuit's constraint logic or the Poseidon parameter provenance. For that depth, see `full_product_breakdown.md` §6 and §18, and the full circuit/contract test suites (`circuits/test/`, `contracts/sharibo/src/test.rs`), both runnable from source per the main README.
