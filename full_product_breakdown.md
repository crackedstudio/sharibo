## 1. Executive summary

Sharibo is a private rotating savings circle (ROSCA) on Stellar. Five members each fund a shared pot every round; one member claims the whole pot. The claim is authorized by a **real Groth16 zero-knowledge proof**, verified **on-chain** by a Soroban smart contract using Stellar's native BLS12-381 pairing host functions — not a mock, not a stub, not a trusted server. The proof shows the contract "this claimant is a genuine circle member" without revealing _which_ member, and a per-round nullifier stops the same proof from being replayed. The payout can land on a brand-new address that has never touched the circle before, so on-chain observers see five deposits and one payout with no way to link them.

This is not a simulation of the idea — every piece of it has been exercised for real on Stellar testnet: a genuine proof generated by the real Phase-1 circuit pipeline was submitted to the real deployed contract and accepted; a tampered proof was submitted and rejected; a full 5-member round (via `scripts/e2e.ts`) funded, claimed, and correctly rejected a nullifier replay. Transaction hashes for all of this are in [§4](#4-live-deployment-verified-on-chain-evidence).

## 2. The problem

Every culture has some form of this savings mechanism, and it's not a niche practice — it's one of the most widely used informal financial instruments on Earth: **ajo/esusu** (Nigeria), **tanda/cundina** (Mexico), **susu** (Ghana/Caribbean), **tontine** (West Africa), **junta/pandero** (Peru), **consórcio** (Brazil), **hui** (China/Taiwan), **paluwagan** (Philippines), **chit fund** (India). The mechanics are always the same: fixed contribution per round, one payout per round, rotate until everyone has collected once.

The structural weakness is also always the same: **the group has to trust that the collector each round is legitimate, and that trust is entirely social** — a shared notebook, a WhatsApp group, a person's word. There's no cryptographic guarantee that only an actual, un-paid member can collect, and no privacy: everyone in the group necessarily knows who's collecting each round, because there's no other way to keep the books.

## 3. The solution

Sharibo replaces the social trust layer with a cryptographic one, without changing the mechanic members already understand:

- An admin creates a circle: contribution amount, size (5, for this demo), and a Merkle root committing to the member set (computed off-chain from each member's private identity — the chain never sees member identities, only the root).
- Members fund the pot with a stablecoin-equivalent test token, each a normal, visible on-chain transaction.
- To claim, a member generates a zero-knowledge proof, off-chain, on their own device, that says: _"I know a secret that hashes to a leaf in this tree, and here is a nullifier tied to this specific circle and round."_ They submit that proof — not their identity — to the contract, along with **any address they choose** to receive the payout.
- The contract verifies the proof for real (a BLS12-381 pairing check), checks the nullifier hasn't been used before, and pays out.

The net effect: the chain shows funding activity and a payout, but nothing that links the payout to a specific funder. And because the recipient address is chosen freely at claim time, it can — and in the demo does — belong to a keypair that's never appeared anywhere else on the circle.

## 5. System architecture

```
create_circle(admin, token, root, contribution, size, vk) -> circle_id
        │  root = Merkle root of Poseidon(identityNullifier, identitySecret) leaves,
        │  computed off-chain by the client for every member
        ▼
fund(circle_id, from)  ×5
        │  from.require_auth(); pot += contribution
        ▼
claim(circle_id, recipient, nullifier_hash, external_nullifier, proof)
        │  1. pot == contribution * size                           ("round not funded")
        │  2. external_nullifier == SHA256(circle_id, round) mod r  ("wrong round tag")
        │  3. nullifier_hash unused for (circle_id, ·)              ("already claimed")
        │  4. real Groth16 / BLS12-381 pairing check passes         ("invalid proof")
        │  → mark nullifier used, pay pot to recipient, pot = 0, round += 1
```

**Layers, and where each lives:**

| Layer                           | Location                                                | Responsibility                                                                                             |
| ------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Circuit                         | `circuits/membership.circom`                            | Proves membership + emits a round-bound nullifier                                                          |
| Trusted setup / proving scripts | `circuits/scripts/{compile,setup,prove}.sh`             | Powers-of-Tau, Groth16 zkey, verification key export                                                       |
| Contract                        | `contracts/sharibo/src/lib.rs`                          | Round accounting, nullifier double-spend map, real on-chain Groth16 verification                           |
| Client SDK                      | `packages/client/src/{identity,tree,prove,contract}.ts` | Identity/commitment generation, Merkle tree, proof generation + wire-format encoding, typed contract calls |
| E2E script                      | `scripts/e2e.ts`                                        | Full round against real testnet, Node-side                                                                 |
| Browser app                     | `app/`                                                  | Same SDK, running in-browser — identical proof generation, no server in the loop                           |

All five non-circuit/non-contract layers share **one** implementation of identity/tree/proof logic (`packages/client/`), specifically so there's no risk of the browser and the Node script computing things differently.

## 6. Deep dive: the ZK circuit

### What it proves

Given a private witness (never leaves the prover's device):

- `identityNullifier`, `identitySecret` — the member's private identity, generated client-side, never transmitted anywhere in raw form
- `pathElements[4]`, `pathIndices[4]` — a Merkle inclusion proof for their commitment leaf, in a depth-4 (16-leaf-capacity) tree

And public inputs:

- `root` — the circle's committed member set
- `externalNullifier` — this circle+round's tag

The circuit proves:

1. `leaf = Poseidon(identityNullifier, identitySecret)` really is in the tree that hashes up to `root` (a standard fixed-depth Merkle inclusion proof, same shape as Tornado Cash / Semaphore — at each level, `pathIndices[i]` selects left/right before hashing with the sibling, and a quadratic-selector trick avoids needing a separate multiplexer component per level).
2. `pathIndices[i]` is boolean at every level (`pathIndices[i] * (1 - pathIndices[i]) === 0`) — this is what makes feeding `2` instead of `0`/`1` fail as a test case.
3. `nullifierHash = Poseidon(identityNullifier, externalNullifier)` is output as a public signal.

### Concrete numbers

- **1,452 non-linear constraints, 2,304 linear constraints** (69 template instances, 3,764 wires) — small enough that the whole proving pipeline, including trusted setup, runs in seconds.
- Compiled with a 2^12 Powers-of-Tau (comfortably larger than needed; a 2^11 ceremony would technically fit).
- `membership.wasm` (witness generator): ~957 KB. `membership_final.zkey` (proving key): ~2.2 MB. `verification_key.json`: ~4.5 KB (small enough to commit to git, unlike the zkey).

### The curve: BLS12-381, not BN254 — and why that's the single most important engineering decision in this project

The obvious default for a Circom + Groth16 stack is BN254 (bn128) — it's circom's default field, circomlib's constants target it, and it's what most ZK tutorials assume. Sharibo does **not** use it. Here's why, in the order it was actually discovered:

1. Soroban's host crypto module (`soroban_sdk::crypto::bls12_381`) only exposes accelerated pairing/EC operations for **BLS12-381**. There is no BN254 host acceleration at all.
2. To check whether a _pure-Rust_ BN254 pairing check (no host acceleration, just the `ark-bn254` crate compiled to wasm) could still work, Stellar's own `stellar/soroban-examples/import_ark_bn254` reference example was run and its budget measured: **a single BN254 pairing costs ~560 million CPU instructions**, against Soroban's standard 100 million instruction budget. Groth16 verification needs several pairings' worth of work (structured as one batched product-of-pairings check), so this isn't "expensive," it's flatly impossible within the protocol's per-transaction ceiling — no amount of extra transaction fee buys past a hard instruction cap.
3. Stellar's own `groth16_verifier` reference example (the one the original build spec itself links) verifies over BLS12-381, using `env.crypto().bls12_381().pairing_check(...)` — confirming this is the intended, and only computationally viable, path.

So the entire circuit, trusted setup, and contract were built for BLS12-381 from the start. The measured cost of a **real** `claim()` call with a real proof and 3 public signals: **48,066,196 out of 100,000,000 CPU instructions (~48%)** — comfortable margin, dominated by `Bls12381Pairing` (~30.3M) and two `Bls12381G1Mul` calls (~7.4M, one per non-fixed public signal in the verification key's linear combination).

### Poseidon over BLS12-381 — provenance

circomlib's Poseidon implementation hardcodes round constants generated specifically for the **BN254** scalar field (this is stated explicitly in the constants file's own generation comment). Those constants are not valid for BLS12-381 — Poseidon's security depends on round constants generated correctly for the specific field in use, and there's no safe shortcut to "port" BN254 constants to a different modulus.

Rather than hand-run the reference Grain-LFSR constant generator under hackathon time pressure (a real, but slow and error-prone, option), Sharibo uses a third-party pair of packages, by the same author, built specifically for this: [`poseidon-bls12381-circom`](https://github.com/jmagan/poseidon-bls12381-circom) (circuit side — `Poseidon255(2)`) and [`poseidon-bls12381`](https://github.com/jmagan/poseidon-bls12381) (TypeScript side — `poseidon2([a, b])`). Both were sanity-checked before being trusted:

- Their hardcoded field modulus (`0x73eda753...00000001`) was cross-checked, independently, against **Soroban SDK's own** `BLS12_381_FR_MODULUS_BE` constant found by reading the installed `soroban-sdk` crate source — exact match.
- The circuit's structure was read directly: 8 full rounds + 56 partial rounds, `x^5` S-box — the standard shape recommended by the Poseidon paper for this field and arity.

Neither package has an independent third-party security audit. This is disclosed, not hidden — see [§18](#18-honest-limitations).

### Circuit interface (as implemented)

```
template MerkleTreeChecker(levels) { … }       // generic depth-`levels` inclusion proof

template Sharibo(levels) {
    signal input identityNullifier;             // private
    signal input identitySecret;                // private
    signal input pathElements[levels];          // private
    signal input pathIndices[levels];           // private, boolean-constrained

    signal input root;                          // public
    signal input externalNullifier;             // public

    signal output nullifierHash;                // public (output)
}
component main { public [root, externalNullifier] } = Sharibo(4);
```

## 7. Deep dive: the smart contract

### Storage

```rust
struct Circle {
    admin: Address,
    token: Address,
    root: Fr,                    // BLS12-381 scalar field element
    contribution: i128,
    size: u32,
    round: u32,
    pot: i128,
    vk: VerificationKey,
}
struct VerificationKey { alpha: G1Affine, beta: G2Affine, gamma: G2Affine, delta: G2Affine, ic: Vec<G1Affine> }
struct Proof { a: G1Affine, b: G2Affine, c: G1Affine }

enum DataKey { NextCircleId, Circle(u64), Nullifier(u64, Fr) }
```

`Fr`, `G1Affine`, `G2Affine` are Soroban's own BLS12-381 types (`soroban_sdk::crypto::bls12_381`), not a custom encoding — `G1Affine` is 96 raw bytes (`be_bytes(X) || be_bytes(Y)`), `G2Affine` is 192 raw bytes, `Fr` is backed by a `U256` and auto-reduces modulo the scalar field on construction.

### Functions

- **`create_circle(admin, token, root, contribution, size, vk) -> circle_id`** — `admin.require_auth()`; stores a new `Circle` at the next sequential id.
- **`fund(circle_id, from)`** — `from.require_auth()`; transfers `contribution` of `token` from `from` into the contract; `pot += contribution`.
- **`claim(circle_id, recipient, nullifier_hash, external_nullifier, proof)`** — **no auth required from the claimant** (deliberate — the ZK proof itself is the authorization, not a Stellar account signature; the transaction's fee-paying source account can be anyone, e.g. a relayer). Checks run in this exact order:
  1. `pot == contribution * size` → else `Error::RoundNotFunded` (2)
  2. `external_nullifier == compute_external_nullifier(circle_id, round)` → else `Error::WrongRoundTag` (3)
  3. `(circle_id, nullifier_hash)` not already recorded → else `Error::AlreadyClaimed` (4)
  4. `verify_groth16(vk, proof, [nullifier_hash, root, external_nullifier])` → else `Error::InvalidProof` (5)
     Then: mark the nullifier used, transfer the pot to `recipient`, zero the pot, increment the round.
- **`get_circle(circle_id) -> Circle`** — plain read.

### The real verifier

```rust
fn verify_groth16(env: &Env, vk: &VerificationKey, proof: &Proof, public_inputs: &Vec<Fr>) -> bool {
    let bls = env.crypto().bls12_381();
    let mut vk_x = vk.ic.get(0).unwrap();
    for i in 0..public_inputs.len() {
        let term = bls.g1_mul(&vk.ic.get(i + 1).unwrap(), &public_inputs.get(i).unwrap());
        vk_x = bls.g1_add(&vk_x, &term);
    }
    let vp1 = vec![env, -proof.a.clone(), vk.alpha.clone(), vk_x, proof.c.clone()];
    let vp2 = vec![env, proof.b.clone(), vk.beta.clone(), vk.gamma.clone(), vk.delta.clone()];
    bls.pairing_check(vp1, vp2)   // e(-A,B) * e(alpha,beta) * e(vk_x,gamma) * e(C,delta) == 1
}
```

This is the standard Groth16 verification equation, checked via Soroban's native pairing host function — a line-for-line match (adapted to this project's type names) of Stellar's own `groth16_verifier` reference implementation. There is no stub, no `// DEMO MOCK:` comment, no shortcut here.

### `compute_external_nullifier` — SHA-256, not Poseidon, and why that's fine

```rust
fn compute_external_nullifier(env: &Env, circle_id: u64, round: u32) -> Fr {
    let mut bytes = Bytes::new(env);
    bytes.extend_from_array(&circle_id.to_be_bytes());
    bytes.extend_from_array(&round.to_be_bytes());
    Fr::from_bytes(env.crypto().sha256(&bytes).to_bytes())   // Fr::from_bytes auto-reduces mod r
}
```

This binds a proof to a specific `(circle_id, round)` so it can't be replayed against a different round. It uses SHA-256, not Poseidon, and that's a **deliberate, permanent** choice, not a leftover placeholder: Soroban has no native Poseidon host function at all, so hand-porting a Poseidon permutation into pure Rust here would only be for aesthetic consistency — there's no efficiency gain, because this check happens outside the SNARK circuit, where "SNARK-friendly" stops mattering. SHA-256 is a native, accelerated Soroban host function and is exactly as cryptographically sound for this binding purpose. Poseidon is used precisely where it earns its keep: _inside_ the circuit's constraint system, where a hash like SHA-256 would cost dramatically more constraints than Poseidon does.

### Error codes

| Code | Name             | Meaning                                                      |
| ---- | ---------------- | ------------------------------------------------------------ |
| 1    | `CircleNotFound` | No circle at that id                                         |
| 2    | `RoundNotFunded` | `pot != contribution * size`                                 |
| 3    | `WrongRoundTag`  | `external_nullifier` doesn't match this circle+round         |
| 4    | `AlreadyClaimed` | This nullifier has already paid out (any round, this circle) |
| 5    | `InvalidProof`   | The Groth16/pairing check failed                             |

Note the nullifier map is keyed `(circle_id, nullifier_hash)` with **no round component** — reusing a nullifier across _different_ rounds is also blocked, as defense-in-depth beyond what's cryptographically implied.

## 8. Deep dive: the client SDK

`packages/client/` is deliberately **isomorphic** — the exact same code runs in `scripts/e2e.ts` (Node) and `app/` (browser), so there is exactly one implementation of every privacy-critical computation, not two that could silently drift apart.

- **`identity.ts`** — `generateIdentity()` (fresh `identityNullifier`/`identitySecret`/`commitment` via `globalThis.crypto.getRandomValues`, not `node:crypto`), `computeExternalNullifier()` (async, `crypto.subtle.digest("SHA-256", …)`, matching the contract exactly — verified byte-identical against the previous Node-`crypto` implementation before switching), `computeNullifierHash()`.
- **`tree.ts`** — a plain in-memory Merkle tree (`MerkleTree.create(levels, leaves)`), padding to `2**levels` with a fixed zero value, producing `{root, pathElements, pathIndices}` for any leaf index. Uses the exact same left/right convention as the circuit's `MerkleTreeChecker`.
- **`prove.ts`** — wraps `snarkjs.groth16.fullProve`, and encodes the resulting proof/verification-key into the contract's exact wire format: `Uint8Array` (not `Buffer` — browser-safe), big-endian per-coordinate, matching Soroban's documented `G1Affine`/`G2Affine` byte layout exactly (no manual flag-bit handling needed, since canonical field elements' reserved flag bits are naturally 0).
- **`contract.ts`** — thin typed wrappers (`connect`, `createCircle`, `fund`, `claim`, `getCircle`) over `@stellar/stellar-sdk`'s `contract.Client`, which pulls the contract's method spec live from chain rather than from a hand-maintained copy that could drift. `basicNodeSigner` handles signing from a raw `Keypair` — no browser wallet extension needed, appropriate for a demo where the app itself manages all the (testnet-only, freshly generated) identities.

## 9. Deep dive: the frontend

`app/` is a single linear flow, intentionally not a general-purpose dashboard: landing (name-wall + one-liner) → generate identities → create circle → fund (5 buttons + pot bar) → pick claimant → prove & claim → claim-again (rejection demo). Two things were added specifically to make the privacy property _visible_ rather than merely _stated_:

- **A step tracker** (Create → Fund → Prove & Claim → Unlinked) so the current stage is always obvious without reading paragraphs.
- **A member ring** — the 5 members render as nodes around a circle. Critically, after a successful claim, **no node is highlighted as "the one that claimed"** — the ring stays visually uniform, and a new node appears _outside_ the ring, connected only to the pot in the center, never to any individual member. This is a deliberate design choice: the UI itself refuses to visually leak which member claimed, reinforcing the actual on-chain property rather than contradicting it for the sake of a flashier demo.

The proving state also surfaces real technical detail (`Groth16 · BLS12-381 · 1,452 constraints`) while the actual computation runs, rather than a generic spinner — because it _is_ real computation, and hiding that behind generic UI would undersell the thing that's actually hard here.

Two browser-specific runtime bugs were found and fixed by tracing dependency source rather than by click-testing (see [§18](#18-honest-limitations) for what wasn't verified): `@stellar/stellar-sdk` needs `Buffer`/`global` polyfilled (Vite doesn't do this automatically); `snarkjs`'s file-loading dependency (`fastfile`) branches on the webpack-era `process.browser` global to decide `fetch()` vs Node's `fs`, which doesn't exist under Vite by default and would otherwise crash proof generation with `process is not defined`. Both are shimmed in `app/src/main.tsx`.

## 10. Cross-cutting invariants

These must agree, byte-for-byte or value-for-value, across circuit, contract, and client — this is the actual thing that would silently break the system if violated:

- **Curve:** BLS12-381 scalar field, everywhere.
- **Commitment:** `leaf = Poseidon(identityNullifier, identitySecret)`.
- **Nullifier:** `nullifierHash = Poseidon(identityNullifier, externalNullifier)`.
- **Round tag:** `externalNullifier = SHA256(circle_id, round) mod r` — SHA-256, specifically _not_ Poseidon (see §7).
- **Public signal order:** `[nullifierHash, root, externalNullifier]` — this is what circom/snarkjs actually emit (circuit _output_ first, then declared public _inputs_, in source order), not the more intuitive-looking `[root, externalNullifier, nullifierHash]` a naive reading of the spec would produce. This was discovered empirically by inspecting a real `public.json`, not assumed.
- **Wire format:** `G1Affine` = 96 bytes (`be(X) || be(Y)`), `G2Affine` = 192 bytes (`be(X_c1) || be(X_c0) || be(Y_c1) || be(Y_c0)`) — Soroban's documented format, which happens to match the widely-standardized ("ZCash-style") BLS12-381 serialization used across the ecosystem.

> **Single source of truth:** The complete specification of all cross-implementation encodings — public signal order, external nullifier derivation, G1/G2 byte encoding, and vk.ic length rules — lives in [`docs/wire-format.md`](docs/wire-format.md), validated by committed test vectors in `test-vectors/wire-format.json`. Each implementation points there instead of describing the format inline.

## 11. Security properties

| Property                                                                   | Enforced by                                                                                                                                                         |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Only a genuine circle member can produce a valid proof                     | Groth16 soundness — the circuit's Merkle inclusion constraint                                                                                                       |
| A proof can't be replayed within the same round                            | Nullifier map keyed `(circle_id, nullifier_hash)`                                                                                                                   |
| A proof can't be replayed against a _different_ round with a different tag | `external_nullifier` bound to `(circle_id, round)` via `compute_external_nullifier`, checked before the nullifier lookup                                            |
| A proof generated for one circle can't be used against another             | `root` and `circle_id` are both baked into what's checked (root via the vk/public-input binding, circle_id via the nullifier key and external_nullifier derivation) |
| The pot can't be claimed until fully funded                                | Explicit `pot == contribution * size` check, first in line                                                                                                          |
| A tampered proof or forged public input is rejected                        | Real pairing check — verified in practice by perturbing `nullifier_hash` and observing `InvalidProof`                                                               |
| Funding requires the funder's real signature                               | `from.require_auth()` in `fund`                                                                                                                                     |
| Circle creation requires the admin's real signature                        | `admin.require_auth()` in `create_circle`                                                                                                                           |

## 12. Privacy properties and their limits

**What's private:** which of the `size` members is claiming in a given round. An on-chain observer sees a valid proof and a payout; nothing in the transaction, the proof, or the public inputs identifies the claimant among the member set. The recipient address is chosen freely and can be (and in the demo is) fresh.

**What's _not_ private, on purpose (scope, not oversight):**

- **Funding is fully public.** Five deposits from five known addresses are visible on-chain; only the _payout_ side is anonymized. Hiding who funded is a materially different (and harder) problem — shielded deposits — and is explicitly out of scope for this build.
- **The member set size and the circle's existence are public.** The Merkle root, contribution amount, and round number are all public contract state.
- **The demo operator necessarily knows who's claiming**, because the demo UI has the person running it pick the claimant via a radio button — the privacy property is about what an _external, on-chain observer_ can determine, not about hiding the choice from whoever is operating the wallet software making the claim (that's true of every ZK system; the prover always knows their own witness).

## 14. Key engineering decisions and deviations

The original build spec assumed a fairly standard BN254 + Poseidon-everywhere ZK stack. Reality diverged from that assumption in a few load-bearing ways, each discovered by testing rather than assumed:

1. **BN254 → BLS12-381** (§6) — the single biggest pivot, driven by a hard CPU-budget wall, not a preference.
2. **Poseidon constants sourced from a third party** (§6) — a direct consequence of #1; circomlib doesn't have BLS12-381 constants.
3. **`compute_external_nullifier` uses SHA-256 permanently, not Poseidon** (§7) — a deliberate simplification once it was clear there's no native Poseidon host function to make matching hash choices worthwhile outside the circuit.
4. **Public signal order is `[nullifierHash, root, externalNullifier]`**, discovered empirically, not `[root, externalNullifier, nullifierHash]` as a first reading of the spec might suggest (§10).
5. **`stellar-sdk`'s `TokenInterface::transfer` takes a `MuxedAddress`, not `Address`**, in the currently-installed SDK version — handled via the standard `From<Address> for MuxedAddress` conversion, transparent at call sites.
6. **Two browser-runtime-only bugs** (`Buffer`/`global` and `process.browser`) found by reading dependency source rather than by click-testing (§9, §18).

Every one of these is also logged, with more raw detail and the exact commands used to discover them, in `NOTES.md`.

## 18. Honest limitations

- **One round demoed, not multi-round.** No on-chain turn-ordering enforcement across rounds.
- **Claim-side privacy only** — funding is fully visible; see §12.
- **Testnet + test token only** — native testnet XLM stands in for a real stablecoin.
- **Single-contributor trusted setup ceremony**, not a real multi-party one — fine for a demo, not for anything real.
- **Third-party, unaudited Poseidon-over-BLS12-381 constants** — cross-checked against Soroban's own field constant, structurally reviewed, but not independently audited (§6).
- **`compute_external_nullifier` uses SHA-256, not Poseidon** — a deliberate, disclosed, permanent choice (§7), not an oversight.
- **The browser app was not click-tested in an actual browser this session** — the browser automation tool was unavailable throughout. What _was_ verified: clean typecheck, clean production build, correct static-asset serving, and the real snarkjs `fetch()`-based proof-generation path exercised end-to-end from Node (forcing the same `process.browser` code branch a real browser takes), producing a proof that verified successfully. Real DOM rendering and click interactions were reviewed by reading the code, not by observing them run. **Verify the click-through yourself before demoing live.**
- Every `// DEMO MOCK:`-flavored decision is disclosed inline in code comments and cross-referenced in `NOTES.md` — nothing is silently faked.

## 19. Roadmap

- Funding-side shielding (hide who funded, not just who claimed).
- Multi-round automation / on-chain turn ordering.
- A real multi-party trusted setup ceremony.
- Independent audit of the BLS12-381 Poseidon parameters, or a switch to self-generated / better-provenanced constants.
- A real issued/stable test asset instead of native testnet XLM.
- **Selective disclosure ("view key")** — an admin/auditor could prove a circle's _total_ historical contributions (a sum over funding events that are already publicly visible on-chain) without exposing which individual funded which round. Not built, but it's a separate read path over already-public data and doesn't touch the claim-side anonymity set at all — described here rather than built, given the time available.
